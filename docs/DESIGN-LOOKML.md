# Design note. A native LookML reader

Date. 2026-11-25. A design record for the one reader the cross ecosystem programme deferred, written before any build, in the same discipline as the attestation note. The Looker slice reads the API's assembled JSON and states a native LookML reader as its boundary. This note scopes that reader.

Why it is its own project. LookML is a real language, not a serialization. Files declare views, explores, and models in blocks with named children, properties whose values are barewords, quoted strings, lists, or raw SQL terminated by a double semicolon, comments, and string interpolation carrying field references. A reader that guesses at this shape with text matching would grade fiction. The reader therefore has three honest parts, a lexer, a block tree parser over the lexer's tokens, and the mapping from tree to grading model, each testable on its own.

The grammar subset, stated as the scope. Blocks of the form kind, colon, name, braces, covering view, explore, dimension, measure, dimension group, join, set, and parameter. Properties of the form key, colon, value, where a value is a quoted string, a bareword, a number, a bracketed list of barewords and strings, or a SQL chunk running to the double semicolon terminator. Hash comments to end of line. References of the form dollar brace name inside SQL chunks and strings, which the lexer records rather than expands, because expansion is Looker's job and the reference itself is the gradeable fact. Everything outside the subset, derived table SQL internals, Liquid templating, refinements and extends in their full generality, is carried as opaque text or named unsupported, never silently misread. A file the subset cannot lex is a reader error, reported as such, not a partial grade.

The tree. Parsing produces blocks with a kind, an optional name, ordered properties, and ordered children, preserving source order because grading output should be stable and reviewable. The tree is the reader's public intermediate, so a later slice can grade surfaces this one does not map, sets and parameters among them, without reparsing.

The mapping, onto the existing model with no new families. A view is a model. Its dimension and measure blocks are items carrying label, description, and the synonyms list as alias claims, exactly as the API reader treats them, so a model graded from its files and from the API document must agree where both describe the same fields. An explore is a relationship source, its joins graded for dangling targets as before. One genuinely new surface appears, and it is native to the files. A measure whose SQL references a field, the dollar brace form, claims that field exists, so references extracted from measure SQL become measure references in the model, excluding the TABLE pseudo reference, and the existing dangling family grades a measure built on a field its view does not define. That defect is invisible in the API document shape the current reader consumes and common in real projects, which is the build's justification.

The gate. Planted LookML fixtures in real file shape. A clean project, two views and an explore, grading clean. A measure referencing an undefined field producing exactly one dangling finding. The synonym collision and dangling join fixtures from the API slice re-expressed as files, grading to the same findings, which is the cross form equivalence this programme has used since the Ossie YAML slice. Lexer unit tests for the terminator rule, comments inside SQL chunks, and interpolation capture.

Build order inside the project. Slice 1 is the lexer, the tree, and the view and explore mapping above, with its gate. Slice 2, if the first proves out, is model files, includes, and extends resolution. Nothing in slice 1 depends on vendor access.
